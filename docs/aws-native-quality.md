# AWSネイティブMCPの品質改善

AWSネイティブ版は [構成・取り込み手順](aws-native.md) を参照。Bedrock Managed Knowledge Baseの標準Retrieveに、公開用の資料目次、完全な出典ページ、画像照合済みの表、正確な検算を組み合わせた。

## 取り込みの確認

3,230文書がすべてINDEXED、失敗0。`python -m aws.managed_status` で受理済みのチェックポイントとは別に確認する。実検索で出典メタデータも確認した。生ログは `tmp/bedrock-managed/index-status.json` と `tmp/mcp-evaluation/native-probe.json` に保存する。

## 完了までの失敗も残す

|段階|画面モード|MULU EA|OPMタイマB|主な問題|
|---|---|---|---|---|
|標準Retrieveのみ・初期取り込み中|不合格|不合格|不合格|分割による表・式の欠落、目的ページへ辿り着けない、矛盾した計算|
|目次・完全ページ・表・検算、mini low|合格|不合格|不合格|MULUで別CPU表へ逸脱、OPMは正答だが未取得の型番を付加|
|調査順序を明示、mini medium|合格|不合格|合格|MULUの38/42と根拠は正しくなったが、ツール上限後に疑似呼び出しが回答へ混入|

それぞれ `native-baseline.json`、`native-verified-core.json`、`native-final-core.json`。初期取り込み中の診断を、全コーパスが固定された同条件のベンダー性能比較とは扱わない。数値が正しくても、根拠未取得・途中計算の矛盾・読みにくいツール断片は合格させない。失敗を消して良い回答だけで置き換えない。

## 原因に対応した修正

- 意味検索のチャンクでは表の後半や式が抜けるため、出典ページの完全取得と、表の全行取得を用意した。前者には全注釈も含まれるので、両方を重複して読む必要はない。
- CPU別の章・ページを公開用の目次で選び、まずRetrieveを1回行い、その後は既に場所の分かったページを読む。推測したページ番号で広い検索を繰り返さない。
- 取得結果のtyped rowsから日本語の可否とMarkdown表を決定的に組み立てる。ハード設定可能とソフト対応、表示解像度とVRAM／色数／ページ数を別々に保持する。
- 検算はPython式のevalを使わず、許可したASTとFractionで有理数として行う。途中値も返す。比較用の複数式は1リクエストにまとめられる。式・単位・CPU適用範囲は計算とは別に原本で確認する。
- 回答役は同じGPT-5.4 miniでreasoning=mediumを試験。採点は独立したGPT-5.4、正解情報は回答役へ渡さない。miniの思考量と明示的な調査手順は [OpenAI公式モデル仕様](https://developers.openai.com/api/docs/models/gpt-5.4-mini)・[ガイド](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.4) を確認した。
- ツール上限6回は維持する。上限後は調査終了を明示し、最終回答を1つのanswerフィールドのJSON Schemaで受け取り、ユーザーにはその文章だけを使う。疑似呼び出しが文章内に残れば固定検査でも不合格にする。
- Native版の評価は、出典付きのBedrock Retrieveを実際に成功させたことも必須にする。ページ取得だけで答えて、ネイティブ検索を試したことにはしない。

## 検証の範囲

既存15問にBcc、DBcc、MC68030 MMUSR B、RESET／PMOVE FDとATCの4問を追加して19問。MC68000UM PDF123の表8-9と、MC68030UM PDF361の表9-3は原本画像でも照合した。PDF362のRESET／FDは本文と照合。これらはAI確認であり、人間の校正ではない。原OCRは上書きせず、新規の正解をMCP本文へ埋め込んでいない。

MCP操作10秒以上、質問開始60秒以上、1回の実行最大3問、同時実行禁止、自動再試行なしを維持する。通常の `make test` はモデルも本番も呼ばない。


## API完了処理と表示単位の追加修正

完了エラーの可視メッセージを調べ、Responsesの複数のcommentaryとfinal_answerを連結していたことを確認した。最終phaseだけを選ぶ処理に修正し、作業メッセージをユーザーの回答やJSONへ混ぜない。当時のWeb版にも反映した。現在の公開リポジトリはAWS／ローカル版を対象とし、旧Web版の実装は含めない。コード中のエスケープは保護し、二重エスケープされたMarkdown改行だけを表示処理で整える。誤った数値を書き換える処理は追加していない。

MSM6258の比較では、検算が正しい7812.5Hzを返しても回答表で3.90625kHzへ書き違える実例があった。最終表示単位のkHzまで式に含めて検算し、highで再確認すると7.8125kHzを含む全行が正しく、全5項目4点となった。LPFの3.4kHzと実機への適用範囲、ADPCM抵抗値もhighで全項目4点。原回答の不合格・完了エラーは `native-final-audio.json`、修正後は `native-final-audio-high.json` に別保存する。思考量と指示の両方を変えているので、どちらか単独の因果効果と断定しない。

構造化表がないページへの空振りを避けるため、資料一覧に `image_checked_table_pages` を追加した。掲載ページ以外は `get_page` を直接使う。元の抽出本文・PDFやKB本文を書き換えず、表取得の可否を公開メタデータとして示すもの。


DMACでは、同書のサンプルCコードに `gcr` メンバがあるだけで、チャンネル0にもGCRがあるとした実誤答を検出した。番地も未回答だった。構造化済みの図3へ辿れるよう、資料一覧に `image_checked_table_catalog`（ページ・図表名・表ID・表題のみ）を追加する。番地や例外の答えを目次に埋め込まず、完全な配置図を実取得して確かめる。コード中の構造体とハードウェア上のチャンネル別配置を区別する指示も加えた。元の不合格は `native-final-registers.json` に保存する。


## 最終確認（2026-11-21）

代表19問の最新回答がすべて合格し、正確さ・根拠・網羅性・実用性・満足度の全5項目で4点だった。回答役はGPT-5.4 miniのmedium（音源3問はhigh）、独立した採点役はGPT-5.4。すべて実際の出典付きNative Retrieveを含む。さらに512×256のハード／IOCS対応と、タイマB=$80の別条件2問をhighで確認し、いずれも全項目4点。後者は4MHzの仮定を明示し32.768msと計算できた。これは選定したケースの最新結果であり、初回成功率や未知の質問すべての正確さを保証する値ではない。

BNEの回答では正しいクロック数だけでは不十分だった。PRM PDF129のBcc命令定義へ案内する目次を追加し、NE条件との対応を実取得してからUM PDF123のタイミング表を使うようにした。目次にクロック数の正解は追加していない。

実回答・点数・取得履歴は `tmp/mcp-evaluation/native-quality-summary.md`（19問）、`tmp/mcp-evaluation/native-heldout-summary.md`（追加2問）。不合格や完了エラーの元ログも保持する。生成された要約時にも現在の固定検査を再適用する。

AWS標準AgenticRetrieveStreamも別途試したが、画面モードのVRAM・色数・ページ数が欠け、採点不合格だった。既定では無効にし、実験用の明示指定だけを残す。標準Retrieve＋完全ページ／表／検算を主経路とする。

この品質バッチ実施時にはPython 74件と旧Web版の検査が成功した。現在の `make test` はPythonのオフライン検査のみ。最新の件数は実行結果を参照し、本番MCP・有料モデルは呼ばない。
