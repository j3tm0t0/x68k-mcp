# X68000 開発知識の範囲と設計

## 到達点

本の検索から始め、CPU・ハードウェア・OS・ツール・実装例を横断して、
「どの機種・どの版で成立する情報か」と根拠を返せる開発用 MCP に育てる。
現在実装済みなのは書籍・公式マニュアル PDF のテキスト抽出、ローカル全文検索、stdio MCP、
AWS Bedrock Managed Knowledge Base＋AgentCore Gatewayの公開HTTP MCP。
出典付きWebメモ、画像照合した構造化表、完全ページ取得と検算ツールも実装済み。
[Issue #1 の必要性評価](priority-assessment.md) に沿って対象を選ぶ。意味検索はAWS版で実装済み。汎用のHTML / Git取得、全資料の自動構造化は未実装。

## 保存する情報

正本は UTF-8 の JSONL と、出典・照合状態を持つ構造化表の JSON とする。DB やベクトルはそこから再生成する。
Markdown は読むための派生物。索引だけに知識を閉じ込めない。

| データ | 内容 |
| --- | --- |
| Source | ID、書名／URL、著者／提供元、種類、版・公開年、ライセンス、取得日、SHA-256 |
| Location | PDF ページ／節／Web 見出し／Git コミット・ファイル・行番号 |
| Chunk | 抽出テキスト、出典位置、文字範囲、品質フラグ |
| Fact（一部実装） | 独立した技術的主張、対象 CPU・機種・OS 版、出典、検証方法・状態 |

書籍ではページ座標の保存、Web では取得日時とコンテンツハッシュ、Git ではコミットの固定を追加する。
資料単位のライセンスだけで足りない場合、ファイルごとの条件を保存する。
検索結果から「メーカー仕様」「書籍の説明」「OSS 実装」「実機での観測」を識別できるようにする。
矛盾する記述は上書きせず、対象機種・版・証拠の違いとして残す。

## テキスト検索から始める理由

開発時の検索は、命令名、関数名、レジスタ名、アドレスなどの正確な一致が重要。
まず [FTS5 の trigram](https://www.sqlite.org/fts5.html#the_trigram_tokenizer) で、日本語を含む部分一致と BM25 順位付けを行う。
現状のチャンクは最大1,400文字、200文字重複、ページをまたがない。節やコードの途中で分かれることはある。
ローカルは全文検索、AWS版は全文・意味のハイブリッド検索を使い、実際の開発質問に対する検索漏れを評価する。

意味検索を追加する際も、技術記号の全文検索を残してハイブリッド検索にする。
埋め込みモデル名・版・次元数を記録し、変更時に再生成可能にする。
文書中に書かれた手順や命令は参考資料であり、エージェントへの指示として実行しない。

## 実装順

1. Inside X68000 で検索の基準を作る。代表的な開発質問を集め、目的のページに到達できるか評価する。
2. NXP の68000資料2件、68060資料3件は追加済み。資料全体の CPU 範囲はメタデータ化済み。命令ごとの対応 CPU の構造化は今後。
3. Web / Git 取り込みを実装し、elf2x68k 等をコミット固定で収録する。
4. アドレス、ビット定義、API、命令を、独自の構造化した事実データとして抽出・照合する。
5. 実質問で検索漏れが残れば意味検索を加える。公開用コーパスと HTTP MCP を構築する。

事実データでは「記載あり」「複数出典で一致」「コード実行で確認」「実機確認」を別の検証状態にする。
OCR や LLM の抽出だけで「検証済み」にしない。
